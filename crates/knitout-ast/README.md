# knitout-ast

A crate that specifies the abstract syntax tree (AST) for the
[knitout](https://textiles-lab.github.io/knitout/knitout.html) machine
knitting language. It is part of the
[knitout-tools](https://github.com/knitout-tools/knitout-tools) repo.

Because knitout isn't a typical language and is more assembly-like, the AST is
more of a vector... but we'll call it an AST still.

If a tool is generating knitout, it's recommended that it generates the AST
directly rather than generating knitout text and then parsing it.

The AST is designed according to the [Trees that
grow](https://simon.peytonjones.org/trees-that-grow/) pattern: nodes in the
tree can be replaced with unknown types (`P::Other`), and are attached with
default types (`P::Foo`). These types come from a `P: Phase` trait
implementation. The "vanilla" AST has `P::Other = Never` (a
bottom/False/underivable type), and `P::Foo = ()` (top/True/unit type). The
crate defines `Valid: Phase`, which has has optional provenance information for
each of its nodes---where in a source file the text came from, or some string
that describes how it was directly generated by a tool.

A basic converter from one `Phase` to another is provided in
`phase_transform.rs`. This is useful for transforming an AST that *might*
contain holes (`P::Other`) into a `Option` of an AST that *cannot*, by
construction, contain holes (like `Valid`).

The `Valid` AST is meant for compiler use, not human-facing linting or formatting.
There are no comments in `Valid`; however, there is support for provenance
information through the `;!source: ` special comment. The AST can be
parameterized to be more useful for those purposes---for example, missing nodes
with errors of type `P::Other`, or additional comments of type `P::Operation`
attached to each operation.

The expanded operations `drop`, `amiss`, and `xfer` are included in the AST.
This is because this crate is primarily meant to represent knitout *programs*
rather than knitout *semantics*. Additionally, expanding them to their
directioned equivalents could cause faults in later stages of, say, a compiler
that doesn't check for empty carrier sets.

Because this is meant to be just an AST representation, there is no support for
an API to construct a program through easy builder methods (what's been called
a "front end" by other knitout projects).

There is support for displaying a `Valid` knitout AST as a canonical string:
the top-level `Program<Valid>` implements `Display`.

No semantic validation (e.g., needles are aligned during `split`) is provided
by this crate. Syntactic validation is also not provided outside of the rigid
program structure; this means, for example, that an `in` operation might be
constructed with no carriers. However, most syntactic woes are bypassed by the
use of this crate.
